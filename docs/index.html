01/the trust problem

Local agents put your workstation inside the blast radius.

If an agent can generate code, open SSH sessions, and read your secrets, your laptop is the security boundary — and there isn't one.

  • Implicit trust Most runtimes execute tools, edits, and commands directly on the user's machine. There is no enforced boundary between the agent and your system.
  • Unbounded access An agent that can SSH into infrastructure typically inherits whatever credentials your shell has. Mistakes scale fast — across every host you can reach.
  • No audit trail Local action logs are easy to lose, easy to skip, and impossible to enforce. Reviewing what an agent actually did becomes detective work.
02/architecture

One trust boundary, enforced before execution.

Users talk to Mantis through Telegram or web chat. The Agent Loop reasons through the LLM and proposes tool calls. The Guard authorizes each call against capability profiles — denied calls stop before execution. Allowed calls fan out to per-task agents that SSH into in-cluster sandboxes (base, browser, ffmpeg, python, db). The same scoped SSH reaches your external servers. Every step lands in PostgreSQL.

03/use cases

Operational tasks, not chat-shaped novelty.

Narrow, credible infrastructure work — the kind you'd otherwise script, ticket, or page someone for.

Fleet diagnostics

Run diagnostics across many hosts from isolated sandboxes; get a clear summary, not raw terminal noise.

> why is api-edge-7 dropping connections?

Infrastructure audits

Sweep configs, certs, services, and exposed ports with findings stored in audit-friendly form.

> list hosts with sshd PasswordAuthentication on

Scripted remediation

Restart services or apply playbooks via skills declared in the guard profile; everything outside the whitelist is rejected.

> restart nginx on edge-* if last 5xx rate > 2%

Specialized sandboxes

Pick the right environment per task: base for SSH/CLI, browser for web checks, python for scripting, ffmpeg for media, db for SQL clients.

> use python sandbox to parse last night's nginx logs

Safe remote execution

Execute from cluster sandboxes, not your laptop, via scoped SSH and per-connection credentials.

> tail journald on prod-db-1 since 14:00

Operational reports

Send short, traceable notifications to Telegram or web with links back to the exact run.

> notify if any node OOMs after deploy
04/guarded automation

Turn one safe run into a reusable plan. Schedule it. Keep the same guard.

Plans add branching, retries, typed parameters, and cron triggers — but they do not bypass the boundary. The same guard that checks a chat-triggered run also checks every scheduled step before it executes.

plan · nightly-disk-watch cron · 0 3 * * * guard · ops-default
every action node passes through the same guard before it executes
Visual editor React Flow canvas with action and decision nodes, branching, retries, and clear-context steps; a real graph editor, not a textarea.
Cron triggers Each plan can run on a schedule. Same execution path as a manual run, same guard, same session logs.
Typed parameters Plans declare JSON Schema inputs; node prompts use Go templates like {{.target}} for dynamic values.
Agent-authored plans The chat agent can write multi-step plans in a small DSL, including scheduled tasks — review and run, or edit and run.
05/guardrails

Concrete controls, not security vibes.

The boundary isn't a policy doc — it's wired into how the runtime executes.

Isolated sandboxes

Every agent runs in a dedicated container — base, browser, python, ffmpeg, db — with a curated tool surface, separate from the host.

Guard profiles

Capabilities and command whitelists are declared per host. The guard inspects every command and rejects anything outside the profile.

Deny by default

The guard is deterministic: only declared skills and whitelisted commands pass. Free-form shell on production never happens.

Constrained SSH

Sandboxes reach your servers over SSH using scoped users and keys configured per connection, not whatever your shell happens to have.

Session logs

Every prompt, tool call, step, and guard decision is persisted per connection, per session — queryable in the UI and the database.

Hard limits

Per-message timeouts, per-step timeouts, and tool-call budgets keep runaway loops contained, with explicit, traceable stop reasons.

08/deploy

Cloud-hosted by design.

Mantis is shipped as a Helm chart. It runs where your other infrastructure runs — not on the operator's laptop.

helm · install
export TAG=$(git rev-parse --short HEAD)
export REGISTRY=ghcr.io/your-org

docker build -f Dockerfile.prod \
  -t ${REGISTRY}/mantis:${TAG} .

docker push ${REGISTRY}/mantis:${TAG}

helm upgrade --install mantis ./helm/mantis \
  --namespace mantis --create-namespace \
  --set app.image.repository=${REGISTRY}/mantis \
  --set app.image.tag=${TAG} \
  --set secrets.authToken='change-me'
Kubernetes-native runtime Sandboxes are pods. Short-lived, replaceable, observable through the same tools you already use.
Off the operator's laptop Control plane, guard and sandboxes all live in the cluster. Your machine isn't on the path.
Single-host friendly too Running a homelab? docker compose up brings up the full stack — sandboxes included.
Bring your own model Any OpenAI-compatible API works — cloud or local. Fallback presets are first-class.
